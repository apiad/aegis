The journal: implementation plan

The work for issue #289: a journal derived from the transcript stores, kept in <state>/journal.db, with journal_search and journal_note for agents, a Journal view, and a Journal row in the sidebar. A hook spike for claims (#290) runs first because claims depend on it; claims get their own plan once the spike has answered.

specdocs/superpowers/specs/2026-10-10-journal-and-claims-design.html. Executors read both. goalAgents and Alex ask aegis what was done on a day or under a path, and no agent writes a journal line by hand. architectureA pure Deriver turns each session's store records into rows. Live, Session._record hands every stored record to a writer thread through a new Host.recorded hook. A backfill feeds the same records from every store. Rows are keyed by (log id, record, ordinal), so both paths insert the same rows and a repeat does nothing. stackPython 3.13, stdlib sqlite3 with FTS5 (3.50.4 on the dev box), pydantic op params, Typer, plain ES-module client, pytest with the fake claude and Playwright. branchjournal-claims-design in the worktree repos/aegis/.claude/worktrees/journal-claims-design, which already carries the spec. The PR for #289 is opened from it.

Global constraints

  • Use uv, never pip. Add no dependency: the journal is stdlib (sqlite3, subprocess, threading).
  • Boot reads no store (DESIGN.md "Boot reads meta files, never stores"). A backfill runs on the writer thread after boot.
  • Never Path.cwd() outside src/aegis/cli.py (tests/test_no_cwd.py); a CLI module calls cli.roots_here.
  • New subsystems add operations and channels, never a protocol field.
  • Client: no <select> or <datalist> (use <pick-chip>), no confirm/alert/prompt, no document or window key listener outside keys.js, every CSS rule scoped #a2 and reading only theme variables, and make site-css after any base.css change.
  • Sidebar rows exist in index.html at boot; side.js wires only those.
  • A test that runs over 3 s without @pytest.mark.slow fails the fast lane.
  • Commits: conventional, English, one logical change, git commit -- <paths>, never amend, never git add -A.
  • Prose in docs, docstrings and the changelog follows the workspace's unslop rules.

Where this plan departs from the spec

  • Agent results name the session's handle, not an entry pointer. peer_read takes only a handle (agent_ops.py:117), so a pointer would be unusable. The entry id goes to the browser, which opens the transcript at it.
  • Closing a session writes a close record, and renaming an open one writes a name record. Today both change only the meta, so a rebuild could not see them. A closed session's transcript gains a "closed" row as a result.
  • journal_note writes its own store record instead of the journal reading the tool call. MCP tool names differ by harness; a record looks the same from all three.
  • The sidebar row fetches through journal.rows instead of riding on the session card, so a journal write never republishes the sessions channel.

Task 13 updates the spec page to match.

Added while executing:

  • A pattern FTS5 cannot parse is searched as literal words. Each whitespace-separated word becomes a quoted phrase, so filenames like notes.md and *.py work. bad_pattern now only answers input that fails even then, such as a NUL. This supersedes review focus 2 below, and a deliberate FTS operator typo now becomes a literal search.
  • Plan rows use transition semantics. A row each time an item turns done (done now, not done in the previous plan), not once per text for the whole session. An item toggled done, undone and done again gives two rows.
  • The Deriver mirrors the fold's end_turn on exit, stop, server_stopped, reset and close, so Codex and OpenCode turns derive the same live and rebuilt.
  • A finished backfill is recorded in journal.db (PRAGMA application_id), replacing the "fresh database only" trigger. An interrupted or halted backfill resumes at the next start, a rebuild racing a backfill uses a per-run token so a cleared file is never marked complete, a store that raises is logged and skipped without blocking the mark, and a corrupt journal.db is set aside and rebuilt at start. stop() runs off the event loop, behind a stop flag.
  • The journal starts before the sessions boot, so records written at boot (server_stopped) are journaled.
  • A rename leaves last_activity alone and is recorded only when the handle changes.
  • Uncommitted edits in a removed worktree are named, after a rebuild, by their path inside the main checkout, so live and rebuilt differ for those touches. Commits still name their files through git. The spec records this as a known limit.
  • Execution: one implementer at a time in the worktree from task 8 on, after parallel staging swept files once. Commit 56b489c8 carries both task 3's shell fix and task 7's when, query and render; its subject names only the first.

Failure modes the spec implies that no feature test reaches. Each one's pinning test is in the task named after it.

  1. A store written before this change has no handle on its spawn record and no name or close records. Backfilling it must not fail, and its rows take the meta's handle.task 8
